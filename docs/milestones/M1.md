# M1 — Viabilidad de la recompilación y prototipo nativo

**Estado:** M1 técnico completado; HITL-1 pendiente.

M1 demuestra que la ruta N64Recomp + N64ModernRuntime + RT64 es viable para
Tetrisphere NTPE rev0. No representa un port completo ni autoriza avanzar por
suposición a los criterios de M2.

## Evidencia por criterio

1. **Mapa de ejecución.** `m1-static-map.md` y `m1-dynamic-map.md` documentan
   arranque, secciones, candidatos de compresión, funciones, tablas de salto,
   llamadas indirectas y búsqueda de overlays. La traza ares confirmó el
   arranque y objetivos indirectos usados; no observó un overlay en la ruta
   muestreada. El mapa inicial publicable está en `m1-symbol-map.md` y los datos
   de máquina en `config/recomp/`.
2. **Runtime.** `m1-runtime-map.md` clasifica las rutas de sistema/libultra como
   implementadas, delegadas o incompatibles. Un símbolo o destino indirecto
   desconocido termina con diagnóstico JSON, fase, dirección y callsite; no se
   simula éxito.
3. **Recompilación reproducible.** `tools/recomp/generate.py` valida la ROM,
   genera C con el N64Recomp fijado y emite un manifiesto reproducible. CMake
   produce `tetrisphere-m1` con GCC/Clang en Linux y MSVC en Windows.
4. **Gráficos y audio reales.** `m1-microcodes.md` identifica F3DEX para
   gráficos y el ucode de audio con entrada `0x800DE7D0`. RT64 consumió listas
   reales del juego y RSPRecomp produjo PCM estéreo no nulo a partir de tareas
   reales; los opcodes no cubiertos permanecen incompatibilidades explícitas.
5. **Ejecución nativa.** La pasada final llegó a Training interactivo en
   Linux/AMD y Windows 11/NVIDIA; una pasada Linux anterior alcanzó además
   Single/Rescue. En ambos sistemas se presentaron frames RT64, se consumió
   entrada y se midió PCM de música más un transiente de efecto aceptado por un
   dispositivo SDL abierto. Windows se ejecutó
   en la sesión de consola real; Wine/Proton no cuentan como evidencia.
6. **Incompatibilidades acotadas.** Las correcciones de contrato, audio, RT64,
   SDL y MSVC tienen pruebas unitarias/CTest. La deuda no necesaria para esta
   demostración está en `m1-compatibility-backlog.md`.
7. **Entregables.** Las builds privadas, manifiestos de evidencia y paquetes
   auditados se conservan bajo `.local/m1/` y `build/packages/`; la ROM,
   capturas, guardados, PCM y credenciales nunca entran en Git.

## Reproducción y verificación

Los comandos completos de compilación y ejecución están en
`docs/qa/m1-linux-protocol.md` y `docs/qa/m1-windows-protocol.md`. Los
manifiestos están ligados al commit que produjo los binarios, por lo que el
validador recibe un checkout limpio de `a7c369f8`; el commit documental de
cierre puede ser posterior sin alterar esa procedencia:

```sh
python3 -m unittest discover -s tests -v
ctest --test-dir .local/m1/build-linux --output-on-failure
git worktree add /tmp/tetrisphere-m1-build-source a7c369f8
python3 tools/qa/run_m1_demo.py validate .local/m1/evidence/linux-final/manifest.json \
  --evidence-root .local/m1/evidence/linux-final \
  --binary .local/m1/build-linux/tetrisphere-m1 \
  --source-root /tmp/tetrisphere-m1-build-source \
  --rt64-receipt .local/m1/build-linux/rt64-verification.json
python3 tools/qa/run_m1_demo.py validate .local/m1/evidence/windows/manifest-a7c369f.json \
  --evidence-root .local/m1/evidence/windows \
  --binary .local/m1/build-windows-native/tetrisphere-m1.exe \
  --source-root /tmp/tetrisphere-m1-build-source \
  --rt64-receipt .local/m1/build-windows-native/rt64-verification.json \
  --platform windows-x86_64
python3 tools/qa/package_m1.py audit build/packages/*.tar.gz
(cd build/packages && sha256sum -c SHA256SUMS)
```

La pasada final produjo 152/152 pruebas Python y 20/20 CTests. Los paquetes se
generaron dos veces y compararon byte por byte; la auditoría conjunta confirmó
plataformas, commit y build ID idénticos, allowlist exacta, licencias completas
y ausencia de ROM, guardados, credenciales y rutas privadas.

## Límites y riesgos

M1 no acredita sesiones completas, guardado persistente, todos los modos,
multijugador, reconexión de dispositivos, 4K, widescreen ni tasas de
presentación elevadas. Aunque el runtime separa acciones lógicas de familias
Xbox/PlayStation/Nintendo Switch, el frame del juego aún usa arte original N64;
la sustitución dinámica de glifos está registrada como trabajo posterior.
Otros caminos pueden descubrir nuevos destinos indirectos, llamadas libultra o
estados RT64; cada uno debe incorporarse con una regresión y conservar el fallo
explícito mientras no sea compatible.

Al terminar por señal la ejecución Linux de evidencia, el proceso aborta con
`terminate called without an active exception`; ocurre después de guardar
capturas, WAV y log válidos y no afecta la escena demostrada, pero el cierre
ordenado del runtime queda en el backlog y no se oculta como éxito.
